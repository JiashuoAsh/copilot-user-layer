# 双轴审查准则

在审查实现前读取本文件；按受影响的行为选择相关检查，不以固定问题数量为目标。默认只读，报告有证据的真实问题，而非潜在风险清单。

## Standards：正确性、回归与仓库约定

- **逻辑与数据流：** 输入是否正确到达结果；分支、条件、单位、索引、默认值、返回值和调用契约是否一致。跟踪真实调用方，不能只看改动片段。
- **回归与兼容：** 原有有效路径是否改变；公共接口、配置、数据格式和已有调用是否仍满足项目承诺；兼容措施应有实际需求。
- **边界与异常：** 空/缺失/非法输入、边界值、失败重试、超时、取消、部分成功等与改动相关的路径是否正确处理；异常不能掩盖错误或导致静默数据丢失。
- **状态与完整性：** 写入顺序、事务、资源生命周期、重复执行、并发和中途失败是否破坏不变量。仅在路径相关时检查这些问题，不凭空要求事务或并发框架。
- **规范与维护性：** 核对适用的贡献指南、编码规范、测试约定和项目既有设计；区分有明确依据的违反与需要权衡的维护性判断。
- **验证覆盖：** 相关测试是否能暴露所改行为的错误；测试缺失不等于已发生故障，不能将未运行说成失败或通过。

## 异味基线：定义与修正方向

这是固定上游 Fowler 基线的完整方法性定义，不是硬规则。委派 Standards 审查时，将本节十二项及以下两条约束完整粘贴到输入中：

- **仓库规范覆盖基线：** 文档明确认可某种写法时，抑制与之冲突的异味报告。
- **始终是判断：** 标注为 `possible <smell>`，不冒充硬违规；跳过工具已强制的事项。修正方向用于判断和建议，不授权自动重构。结合具体影响，不机械要求抽象或改继承。

每项为“是什么 → 如何修复”的线索：

- **Mysterious Name：** 函数、变量或类型名称不能说明作用或所持数据。→ 重命名；若无法找到真实名称，进一步检查设计是否不清晰。
- **Duplicated Code：** 变更中多个 hunk 或文件出现相同逻辑形状。→ 提取共同形状，让双方调用。
- **Feature Envy：** 方法访问另一对象的数据多于自身数据。→ 将方法移到它所依赖的数据所属对象。
- **Data Clumps：** 同一组字段或参数总是一起传递。→ 把它们组织成一个类型并传递该类型。
- **Primitive Obsession：** 使用 primitive 或 string 代替值得独立建模的领域概念。→ 为概念定义小型专用类型。
- **Repeated Switches：** 变更中反复出现针对同一类型的相同 switch/if 级联。→ 使用多态，或让各处共享同一个映射。
- **Shotgun Surgery：** 一个逻辑变更迫使 diff 在许多文件分散修改。→ 将共同变化的内容聚合到同一模块。
- **Divergent Change：** 一个文件或模块因多个互不相关的原因被修改。→ 拆分，使每个模块围绕一个变化原因。
- **Speculative Generality：** 为规格未要求的潜在需求新增抽象、参数或 hook。→ 移除或内联，直到真实需求出现。
- **Message Chains：** 调用者依赖本不该了解的长导航链，如 `a.b().c().d()`。→ 将导航封装为首个对象上的方法。
- **Middle Man：** 类或函数主要只是向下转发。→ 移除无价值中间层，直接调用实际目标。
- **Refused Bequest：** 子类或实现类忽略或覆盖大部分继承内容。→ 考虑以组合取代该继承关系。

自动工具已报告的同一问题不重复包装成新发现；仍应报告工具未覆盖、可由证据确认的实质性问题。

## Spec：需求与实现对应

- 逐项检查要求是否遗漏、部分实现、理解错误或实现结果不符。
- 检查新增行为是否越出用户要求的范围，区分必要支撑改动与无依据的功能扩张。
- 将需求定位、实现路径和验证证据连起来；没有完整规格时继续审查已知要求，并说明覆盖缺口。

## 报告格式

每项发现写清严重性、所属轴、文件/符号/定位、触发条件、证据、影响及克制的修正建议。两轴分别汇报，汇总时保留各审查者的报告顺序，不跨轴重排。同一问题可共享 ID，但各轴保留自身依据与计数；额外的去重总数只计一次。无发现时说明范围和未验证部分，不输出无依据的“全部正确”。
