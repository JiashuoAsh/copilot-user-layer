# 双轴审查准则

在审查实现前读取本文件；按受影响的行为选择相关检查，不以固定问题数量为目标。默认只读，报告有证据的真实问题，而非潜在风险清单。

## Standards：正确性、回归与仓库约定

- **逻辑与数据流：** 输入是否正确到达结果；分支、条件、单位、索引、默认值、返回值和调用契约是否一致。跟踪真实调用方，不能只看改动片段。
- **回归与兼容：** 原有有效路径是否改变；公共接口、配置、数据格式和已有调用是否仍满足项目承诺；兼容措施应有实际需求。
- **边界与异常：** 空/缺失/非法输入、边界值、失败重试、超时、取消、部分成功等与改动相关的路径是否正确处理；异常不能掩盖错误或导致静默数据丢失。
- **状态与完整性：** 写入顺序、事务、资源生命周期、重复执行、并发和中途失败是否破坏不变量。仅在路径相关时检查这些问题，不凭空要求事务或并发框架。
- **规范与维护性：** 核对适用的贡献指南、编码规范、测试约定和项目既有设计；区分有明确依据的违反与需要权衡的维护性判断。
- **验证覆盖：** 相关测试是否能暴露所改行为的错误；测试缺失不等于已发生故障，不能将未运行说成失败或通过。

仓库约定优先于通用风格偏好。异味仅是调查线索：不明命名、重复逻辑、Feature Envy、Data Clumps、Primitive Obsession、重复分支、Shotgun Surgery、Divergent Change、Speculative Generality、Message Chains、Middle Man、Refused Bequest。先证明具体影响再报告；不机械要求抽象、移动代码或重写继承。

自动工具已报告的同一问题不重复包装成新发现；仍应报告工具未覆盖、可由证据确认的实质性问题。

## Spec：需求与实现对应

- 逐项检查要求是否遗漏、部分实现、理解错误或实现结果不符。
- 检查新增行为是否越出用户要求的范围，区分必要支撑改动与无依据的功能扩张。
- 将需求定位、实现路径和验证证据连起来；没有完整规格时继续审查已知要求，并说明覆盖缺口。

## 报告格式

每项发现写清严重性、所属轴、文件/符号/定位、触发条件、证据、影响及克制的修正建议。两轴分别汇报，轴内按严重性排序；同一问题可标注双轴依据，但只计一次。无发现时说明范围和未验证部分，不输出无依据的“全部正确”。
