# 实验执行与 GPU 调度

跨项目执行规则。先读取当前项目指令、运行协议、启动入口和输出目录约定；权限取当前任务与模式的有效授权，本指令不扩大权限，不要求重复批准已有授权。只检查代码时应用相关审查标准，不启动实验或查询无关 GPU。GPU 调度统一遵循本文件，除非用户明确提出适用范围内的例外；其他角色和文档引用本文件，不另设调度规则。

## 持久运行与记录

- 长实验优先使用项目已有调度器或 `nohup` 等合适方式脱离交互终端；短时命令无需后台运行。不能将仅在当前终端后台运行等同于会话关闭后仍可靠执行；不适合脱离时说明具体限制。
- stdout/stderr 写入该 run 独占的持久日志，按项目约定放置；新运行/报告使用唯一输出，不覆盖历史证据。若入口要求输出目录不存在，不为日志预建该目录；先用独立启动日志，随后关联运行产物。
- 若通用终端规则要求覆盖工作区 `output.txt`，它仅作启动/检查命令摘要；实验原始输出始终保存到 run 日志，不让后续命令覆盖。并行任务各用独立日志和独占摘要路径或由父级串行汇总，不争写共享文件。
- 启动前记录命令、cwd、输入代码/config/数据与协议版本、环境、设备、唯一输出和日志位置；启动后记录主机、PID 加进程起始标识或调度器 job ID、启动时间及退出状态来源。重试前核对已有运行，缺报告不等于未启动。
- 启动后检查进程和初始日志，确认未立即失败；进程启动仅代表 running。完成须核对退出状态、必要产物与项目适用的完整性检查，不以最后一行日志或调用返回推定成功。失败尝试及原始输出保留，不记录秘密值。
- 启动与完成检查的范围、指纹和已验证输入的复用，统一按[实验比较指令](experiment-comparison.instructions.md)的“校验开销与证据复用”执行；同批实验复用可信的共享输入和环境证据，每个 run 仍保留自己的实际配置、运行身份、输出与退出证据，不把全量重复校验作为默认启动门槛。

## GPU 调度

- 启动前核对 GPU UUID、进程类型、命令及用户归属、显存和利用率。以实际用户进程/调度器身份确认“用户自有卡”，不是仅凭本次 Agent 启动记录。含他人训练、评估、推理或其他实际 GPU 工作负载的卡整卡排除，即使同卡也有用户任务或剩余显存；未知进程先核实用途和归属。
- 已确认的低占用系统图形常驻服务（如 `/usr/lib/xorg/Xorg`，类型 `G`、仅数 MiB 显存且无明显 GPU 负载）不算他人实验占卡，不能仅因它以 `root` 运行就阻塞实验。若除此之外没有实际 GPU 工作负载，该卡按空闲卡计；若另有用户自己的任务，可按自有卡判断堆叠。系统服务显存仍计入实际占用，不终止这些服务；不能仅凭进程名、`G` 类型、`root` 身份或显存少就忽略未知进程，也不把他人的实际图形/计算任务当作系统服务。
- 可用卡数指排除他人实际 GPU 工作负载后的“空闲卡＋用户已占用且无他人工作负载的卡”，系统服务按上一条处理；不是机器总卡数，也不随是否能放下新实验而缩减计数。可用卡数不超过 2 张时视为资源紧张，允许不留任何空卡；超过 2 张时通常保留至少 1 张空闲 GPU，不固定卡号，不为满足留卡条件中断既有任务。
- 优先空闲卡并行；可用卡不超过 2 张，或超过 2 张但按留卡规则分配空卡后仍有就绪实验排队时，允许在用户自有卡堆叠独立 GPU 实验（训练、评估或推理）。不能向他人占用的卡堆叠。无需为常规选卡、免留卡或合规堆叠再次询问用户。
- 堆叠前检查当时的同卡进程和显存，结合同配置历史峰值、已有测量或合理估算，判断已有实验和新实验能否容纳并留出余量。显存不足不堆叠，不为塞入同卡擅改正式 batch size、precision 或协议。
- 各独立会话自行完成启动前检查，不要求跨会话统一负责人、共享锁或容量账本，也不因缺少这些机制阻塞启动。检查后仍可能有其他会话同时启动而发生竞争或 OOM；保留失败证据，按实际故障调整本任务新增运行或重试安排，不停止既有健康任务腾卡。
- 并行数量依据 GPU 归属、可用卡数、留卡和显存容量规则，不以 CPU、主机内存或 I/O 检查/容量估算作为启动前置条件，不因这些预估减少并发；实际发生相关故障后按证据调整。单实验多卡仍仅使用已有验证的兼容路径，不为并行更改正式 schedule 或引入未验证分布式路径。
- 同一有状态 continual stream 内的 task 按协议顺序执行，不为并行拆流、重置适配状态或改变预测/更新顺序。
- CPU-only 任务不经过 GPU 调度检查，仍保留授权、去重、固定输入、独占输出及退出证据。

## 状态检查

- GPU 实验启动后先完成立即失败检查；确认日志已进入正常训练/评估且进度开始推进后，每 5 分钟检查一次，直到完成或失败。每次核对已记录的进程/作业身份与存活状态、退出状态、最新日志和 step/epoch 等项目实际进度，并记录当前状态与下一检查时间；不能只因进程仍在就认定实验正常。
- 周期巡检保持轻量：读取状态记录、必要的增量或尾部日志及对应进程信息，不重复遍历数据集、计算全量 hash、加载模型或运行评测，不周期性扫描全部历史产物。只有异常线索才升级为相关诊断；完成时再做适用的结果检查，复用有效证据。
- 收到完成/失败通知立即处理，不等下一个 5 分钟检查点。正常结束后及时核对退出码和必要产物并推进后续工作；异常退出及时保留日志与失败证据，在已有授权内诊断处理，不继续按 running 等待。进程仍在但进度长期不变时，结合项目正常单步/阶段耗时核查停滞原因，不凭一次日志未更新就判失败或终止。
- CPU-only 长任务未收到完成/失败通知时，主动检查仍至少间隔十五分钟；启动立即失败、用户查询或取消不受周期限制。优先使用已有通知、调度器或可用的定时检查机制，不忙等。实验进程可持续不表示 Agent 常驻；当前会话无法继续检查且没有可用监控机制时，如实说明最后状态和监控缺口，不声称会自动按时唤醒。
