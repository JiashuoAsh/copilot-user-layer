# 文档式讨论

让主文档始终呈现当前方案和真正未决的问题，每轮评论都能得到处理，旧讨论不持续堆在正文中。适用于工程、科研和其他方案讨论，不接管领域判断或实施权限。

## 1. 确认材料与维护范围

先读当前请求、已有讨论、关联规范和必要事实。优先沿用用户正在评论的文件与项目记录，不另造一份竞争方案。多文件存在冲突时指出哪份当前有效；不把所在目录自动当作目标项目。

用户要求创建、维护、按评论修改或整理讨论文档时，可在对应文档范围内更新。只问建议时先在聊天给出流程；自动发现技能不授予写入权限。方案讨论、定稿和文档确认均不自动授权实施、训练、提交或外部操作；已有独立执行授权仍有效。

**完成判据：** 已确定讨论对象、有效材料、文件位置和本轮写入范围；能自行核实的事实不留给用户猜答。

## 2. 建立可评论的当前稿

按 [讨论模板](./assets/discussion-template.md) 按需组织内容，已有格式能满足要求时就地维护。没有现有位置约定时，在项目的 `docs/discussions/<topic>.md` 创建一份有实质内容的文档，不预建空目录或多套记录。

- 顶部说明目标、当前轮次、状态及这轮需要用户判断的重点。
- 当前方案给出首选、理由、重要取舍和会改变选择的条件。需要计划时列出具体步骤、依赖和完成判据；尚未确定的下游步骤明确标为暂定。
- 将已核实事实、Agent 建议、用户确认的决定和待验证判断区分开。当前稿是最新提案，不因被写入正文就成为共识。
- 仅列会影响方案的未决问题，每项说明推荐、依据、影响及下一处理动作；通常突出最重要的 1–3 项，不用凑数。
- 需要跨轮引用的条目使用稳定 ID（如 `Q-001`），关闭后不重用编号；普通段落不强制逐句编号。

**完成判据：** 用户能直接定位并评论核心选择，能辨认哪些已确认、哪些只是建议，无须先读历史才能理解当前稿。

## 3. 处理一轮评论并同步修订

用户可以直接在相关段落下写“用户：……”或在聊天中引用标题/条目；不要求专用标记、表格或逐项填写状态。处理前重读文件，识别本轮新增意见，不把旧评论再次当作新决定。

由 Agent 将本轮实质意见与处理结果对应起来；需要跨轮保留的线程补稳定 ID，沿用原条目并标明待回应、待确认、待查证或保留分歧。已有答复且没有新意见的线程不重复处理。聊天评论写入记录时保留原话或明确标为摘要；无法判断是否处理过时先核对现有答复和历史，不猜测用户已经确认。

对每条实质意见给出明确处理结果：按意见修改；有证据地提出不同判断并保留分歧；或说明需要查证/澄清的具体缺口。问题不等于修改指令，沉默、未评论其他段落和“已处理”均不等于用户同意。用户的明确选择只确认其覆盖的范围，不把 Agent 自行补充的方案说成用户决定。

同步修改当前方案、相关步骤和受影响的已确认决定。上游改变时，将依赖的旧决定标为待复核并说明原因；不要只在文末追加答复而让正文继续使用旧方案。重要语义不清时仅暂停依赖该答案的部分，其他明确意见继续处理。

每轮聊天简报：本轮改了什么、未采纳或待查证什么、仍需判断什么；逐项覆盖实质评论，不重复粘贴整份方案。用户要求文档内回应时在相应条目保留简短答复。

**完成判据：** 每条实质意见有可定位的处理结果，正文与处理结果一致，未决分歧和依赖影响没有被隐藏，状态保持为待反馈，直至相应内容被明确确认。

## 4. 每轮收尾，清理已解决讨论

主文档保留当前稿、尚未解决或待确认的评论、仍有效的简短决定及其理由。已完成的动作清单移出未决区；已过时方案从当前稿退出。当前轮次和状态就地更新，不无限追加“第 N 轮全文”。

清理遵循保留优先：

- 对 Agent 自己已被替代的说明可精简。用户原话、实质分歧、被替代的重要决定及其理由，在移出正文前先保存到项目既有历史位置；没有约定时按需使用相邻 `archive/<topic>.md`，按轮次追加原评论、处理结论和对应决定，不复制整份讨论。
- 保存后实际读取核对，再移除对应正文，并留下必要的历史链接。无法确认已保存时保留原文，不以 Git 历史或“聊天里有”替代未提交意见的保护。
- 归档前按源文档、线程 ID 和轮次检查已有记录；中断后重试先核对是否已经保存，相同内容不重复追加，新意见作为该线程的新轮次保存。摘要与用户原话分别标明。
- 未回复、未确认、有歧义的意见继续留在未决区；可以压缩 Agent 的重复答复，不擅自改写用户原话。用户明确要求逐字保留或只读时遵从。
- 旧文档首次整理时，先识别当前方案、开放问题、有效决定与历史；只搬移能判定为历史且已安全保留的内容。状态不明的项目集中为待核对，不强行判为已完成。

写回前复读即将覆盖的片段，对照本轮读取的原文，仅用精确局部修改更新。发现用户又有修改或补丁上下文失效时，重新读取并保留双方内容；无法无歧义合并时保留原状，报告具体冲突，不强行重写整份文件。正文和处理结果实际写入后才能标记本轮完成。这是协作规范，不提供文件锁或原子写入保证。

**完成判据：** 当前稿不含已解决的评论往返或旧版全文，未决项仍可见，重要决定有简短理由，被移走的用户意见可追溯，未覆盖无关笔记。

## 5. 定稿或继续

用户确认后记录确认范围及日期；仍有重要未决项时只能部分确认或暂定。确认后的内容可在后续证据出现时重开，记录原因并复核依赖，不把历史决定悄悄改写。用户明确结束讨论时保留未决项和影响，不强迫达成共识。

定稿时优先将有效内容合入已有规格、计划或研究记录，讨论文档保留简短结果与目标文件链接；没有承接文件时，讨论文档本身可以成为定稿。不要让两份完整方案分别维护，也不为低影响决定逐条创建 ADR。执行授权按当前请求与既有范围判断。

承接前重新读取目标记录，按已有 ID 或主题更新对应条目，不重复追加。只把明确确认的范围写成决定；已核实事实附来源，未确认建议和证据缺口保持原状态。目标记录有更新且无法明确合并时，保留两边并暂停冲突部分。写入并回读核对后，才将讨论稿收为结果、未决项和有效方案链接，简记承接日期及范围。

**完成判据：** 确认范围、剩余问题、当前有效文档及下一步清楚。需要继续时等用户评论；要求整理或定稿时完成本轮文档维护，不用再次询问是否开始。

## 与已有方法衔接

需要压力测试方案时可结合 `grill-me`；跨会话有多项相互依赖的重大未决决定时可结合 `wayfinder`；方案已定且需要拆分实施任务时使用 `to-tickets`。这些方法各自解决不同问题，不要求每次讨论全部调用。科研讨论继续遵守项目记录的单写者和证据状态规则。
