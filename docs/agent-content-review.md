## 判定标准

依据 [writing-for-agents](../skills/writing-for-agents/SKILL.md) 的完整可读要求，并对照[总体规划](research-agent-collaboration-plan.md)与[共享协议](../research-guides/orchestration.md)审查。该 Skill 的“Steps and completion criteria”段当前存在残句；不推定缺失原文，不据此添加未知要求。

| 维度 | 判定问题 |
|---|---|
| 入口与职责 | 何时使用、负责什么、交付给谁，能否与相邻角色区分？ |
| 方法可达 | 必需方法是否有明确的读取时机，分支是否能到达对应参考？ |
| 可执行性 | 启动、派工、放行、失败返回和停止条件是否能据实际状态判断？ |
| 完成证据 | 是否能用答案、来源、测试、产物或运行记录核对完成，而非仅凭调用成功？ |
| 契约一致 | 正文、工具、调用名单和共享协议是否相容，工具可用性是否与授权分开？ |
| 信息层次 | 通用规则是否集中维护，短任务是否有短路径，必要边界是否随执行上下文保留？ |
| 证据范围 | 是否区分配置成立、实际行为验证与科研有效性？ |

语言、字数和模板统一程度不单独决定合理性。重要问题指有具体场景可能导致错误阻塞、漏掉关键核查或违背已确认要求；较轻问题指主要增加工作量或降低交付清晰度，已有规则可部分缓解。潜在触发场景不等于已观察到运行故障。

### AC-001：自主入口把已有假设写成必备条件

**用户决定：** 同意原推荐方案。

**原问题证据：** [自主入口（历史名称）](../agents/research/entry/autonomous-research-orchestrator.agent.md)“启动检查”曾要求实施前必须取得“核心研究目标、问题和假设”；[项目记录规范](../research-guides/project-records.md)则使用“假设（如适用）”。

**触发与影响：** 用户已明确探索目标、评价条件、预算和权限，但尚无机制假设，希望先实现测量、调查现象。当前措辞可能迫使用户先补假设，或诱导 Agent 为启动而构造假设。这是文本要求不一致；该场景尚未专项运行验证。

**实施内容：** 启动项改为“核心研究问题或探索目标；已有假设如适用”，允许明确记录“未预设假设”。描述、输入提示和停止条件同步保留目标稳定性；已有获批假设仍不得擅自更换。其他时间、资源、预算和授权边界未放宽。

**推荐原因：** 保留自主模式的目标稳定性，同时支持合法的探索性研究，不把科学研究强行变成先验假设填表。

**验证条件：**

- 文件及相关引用对“假设可选”的表达一致，未放宽其他授权边界。
- 用有探索目标、无预设假设且其他边界齐全的轻量场景检查：不因缺假设而阻塞或编造假设。
- 对已有获批假设需要更换的场景，仍返回需要用户决定的具体事项。

### AC-002：GPU 设备预留要求可能误挡 CPU-only 实验

**2026-11-03 状态：已被替代。** 用户明确统一调度规则、接受独立会话偶发竞争；现已撤回跨会话启动所有权/共享锁门槛，角色统一读取实验执行指令。以下实施内容和验证条件为历史方案，不再要求验证“缺少共享预留就阻塞 GPU”。

**用户决定：** 同意原推荐方案。

**原问题证据：** [Experiment Lead](../agents/research/coordination/experiment-lead.agent.md)步骤 4、[Experiment Runner](../agents/research/specialists/experiment-runner.agent.md)步骤 3 和[共享协议](../research-guides/orchestration.md)的资源段没有明确区分 GPU 与 CPU-only 运行。

**触发与影响：** 一个已授权、输入固定的 CPU-only 小测量，可能仅因没有 GPU 预留机制或无法确认跨项目启动负责人而被阻塞。这里确认的是适用范围歧义，不声称该误阻塞已经实测发生。

**实施内容：** Lead、Runner 和共享协议现已明确资源分支：GPU 运行需要跨项目启动所有权或共享原子预留；CPU-only 运行不需要 GPU 预留，但仍检查任务授权、重复启动、固定输入、独占输出和退出证据。

**推荐原因：** 设备争用保护应作用于实际使用的资源；不应让 GPU 专用前置条件阻断 CPU 验证，也不应借此取消 GPU 任务的保护。

**验证条件：**

- 三处文本对 CPU 与 GPU 的适用分支一致。
- 无 GPU 预留机制的 CPU-only 轻量任务能在授权范围内推进。
- GPU 任务缺少所需启动所有权和可靠共享预留时，仍返回明确阻塞；无需为检查该分支启动真实训练。

### AC-003：实现前核查缺少明确放行契约

**用户决定与疑问：** 同意实现前放行契约；同时指出 Agent 可能不断细化边界，把本可在实现或实验中解决的问题升级为前置阻塞。

**原问题证据：** [Implementation Lead](../agents/research/coordination/implementation-lead.agent.md)步骤 1 要求将方法转换成状态、接口和验收标准；[批次入口（历史名称）](../agents/research/entry/research-orchestrator.agent.md)允许简单任务直派 Implementer；[共享协议](../research-guides/orchestration.md)原先没有明确实施计划的放行记录，也没有核查结束和重开条件。

**触发与影响：** 已有方法 revision、写入路径和测试指标，但方法到代码的科学条件、状态映射或可行性尚未核查，任务仍可能进入实现。文件已有计划要求；缺口是“编制计划”与“核查后放行”的责任连接，尤其是简单直派路径。

**实施内容：** 共享任务包新增 `release` 字段。root 或 Lead 记录当前 revision 的科学条件、修改/运行范围、关键可行性和验收方式；Implementer 启动前核对该结论。直派短任务也必须提供一句最小放行记录。新增“阻塞项、待验证项、未来优化”分流，以及同一 revision 的复用和按新证据重开规则；不新增固定角色、强制子调用或用户审批关卡。

**推荐原因：** 保留短路径，同时让实现前核查成为可检查的交付，避免以实现后测试代替科学条件核查。共享协议维护完整要求，角色入口只保留必要指针和启动检查，减少多份规则漂移。

**验证条件：**

- 经过 Lead 和直接派给 Implementer 的任务包都能指向当前 revision 的核查结论。
- 缺少核查或核查已过期的场景，不直接开始写源码；在权限内补齐核查或返回具体缺口。
- 记录简单任务可简短，未引入不必要的审批或调用；实现后测试仍独立执行。

#### 有限核查规则

**判断：** 这个担忧应纳入 AC-003，而不只是另加一个时间上限。放行要求若只有“已经核查”，却没有充分条件，确实可能变成持续增加前置条件。这里记录的是用户报告的现象和协议设计风险；没有具体停滞轨迹，不能断言每次停滞的根因相同。

核查只回答“当前这一步能否在授权范围内产生可解释、可验收的结果”，不是提前证明整个研究方向成立。

| 约束 | 推荐规则 |
|---|---|
| 最小放行条件 | 当前交付物、实际依赖的输入版本、允许动作与写入范围、影响本步有效性的关键条件及验收方式已明确；没有尚未处置的实质阻塞即可放行，不要求穷尽未来边界。 |
| 阻塞项举证 | 说明缺什么、影响当前哪个动作或判读、现在推进的具体后果，以及最小解除办法。权限缺失、会使本步结果无效或无法解释的协议歧义、不可逆风险等才应先解决；不能只以“仍有不确定性”为由阻塞。 |
| 待验证项分流 | 不改变本步合法性与可解释性、可由隔离测试回答的问题，记为待验证项并推进。无法区分实现方案时，可先做已授权、可逆、低成本的判别性探针；探针通过不等于科学主张成立。 |
| 放行后复用 | 同一相关输入版本及适用范围的核查结论可复用，不因换会话、换审阅者或措辞不同重做。新证据、相关输入或权限变化才重开受影响部分，注明触发点和影响，不将整个计划退回起点。 |
| 有限核查 | 在当前任务时间与调用预算内选择能改变下一动作的检查。没有新的决策相关信息就停止展开；预算耗尽不等于通过，应返回具体阻塞或提出更小的可执行步骤，不能自行扩大权限。 |

**例子：** 验证在线更新顺序前，预测发生在更新前还是更新后会改变测量含义，需要明确；长期最优学习率、全部数据集表现和未来部署吞吐不必成为该单元验证的启动门槛。若当前问题正是比较两种顺序，则可在既有授权内固定两条分支做对照，无需先证明哪种顺序更优。

**补充验收场景：**

- 非阻塞的未来优化建议不会阻止最小验证；与本步相关的待验证项仍被记录和检查。
- 权限缺失或当前测量会使用不可用标签时，仍阻塞对应动作，或先缩小为不依赖该信息的合法步骤。
- 同版本、无新证据的第二次审阅复用结论；新证据只使相关条件待复核。
- 核查预算耗尽时不强行放行，也不无限递归补条件；返回当前结论、确切阻塞和最小下一步。

**参考边界：** Anthropic 文章支持简单工作流、环境反馈和停止条件等通用原则；它不是本仓库行为已经改善的证据。OpenAI PDF 未能在本轮提取正文，因此不将其在旧对话中的转述作为已核实依据。

### AC-004：局部核对与完整报告模板不匹配

**用户决定：** 同意原推荐方案。

**原问题证据：** [Reproducibility Engineer](../agents/research/specialists/reproducibility-engineer.agent.md)允许 targeted inspection，却缺少明确的短输出分支。[Literature Scout](../agents/research/specialists/literature-scout.agent.md)同样需要区分 bounded lookup 与完整文献地图。[总体规划](research-agent-collaboration-plan.md)O07 已确认短任务按问题返回。

**触发与影响：** 仅核查 checkpoint 是否包含 optimizer state，或确认一篇论文年份和发表状态时，Agent 可能为填满格式而扩展调查、增加无关建议。现有 targeted、when appropriate、concise 等要求可部分缓解，因此定为较轻问题；尚未证明每次都会出现长报告。

**实施内容：** 两个专家的输出入口现已增加短任务分支：局部核对只返回答案、证据位置、关键限制/不确定性和下一步影响；完整评估或文献地图继续使用详细结构。没有把所有专家强行统一为同一模板。

**推荐原因：** 让输出规模服从派工问题，保留完整任务所需深度，减少无关交接内容；泄漏、公平性、状态生命周期等与当前问题有关的检查仍须保留。

**验证条件：**

- 两类任务的触发条件和输出要求明确，无需创建额外文件体系。
- 局部核对不自动扩展为完整研究计划，完整任务仍交付相关详细评估。
- 压缩报告未省略影响当前结论的证据、限制或科学有效性检查。

### AC-005：自主入口把排程参数设成启动必填项

**触发与影响：** 用户反馈自主入口反复询问调度内容，质疑其自动化价值。检查发现自主入口曾把执行时长、GPU/数据/工作区范围、模型调用/费用预算、禁止事项、停止条件和通知事项均列为启动前必须从用户或记录取得，并要求缺少关键边界就停止；`argument-hint` 还示范了“缺失边界先问我”。总体规划也保留“缺一项就先补边界”的旧措辞。这与共享协议“授权持续有效，不重复询问常规可逆步骤”和“常规技术选择不推回用户”不一致。实际反复询问的会话轨迹未纳入本轮核查，因此根因由配置文本直接支持，具体触发频率仍待运行验证。

**用户决定与处理：** 用户先指出自主入口应自动工作，不应持续索取调度细节；随后明确扩大权限：“权限可以多给点，只要记录不缺失，不会把系统或者工作区搞崩就行”。自主入口现自行安排任务顺序、专家路由、调用分配和检查节奏；对明确的项目推进请求，默认授权项目内修改、测试、隔离环境依赖、训练/实验和自身失败进程处置，不再逐项请求执行批准。完整记录和不损坏系统/工作区是执行条件，不是要求用户逐项确认的清单。

**保护边界：** 只讨论、设计或查询状态不触发执行授权。默认授权限于目标项目与隔离环境；不改系统/共享环境，不覆盖未提交用户改动、原始数据、检查点或旧证据，不停止健康任务腾资源，不处理他人进程。GPU 遵循用户既有预留规则。新增付费资源、外部发布、提交推送、破坏性删除/覆盖及越出项目范围的操作仍需授权。用户明确给出的上限优先。

**修改位置：** [自主入口（历史名称）](../agents/research/entry/autonomous-research-orchestrator.agent.md)、[共享协作协议](../research-guides/orchestration.md)、[总体规划](research-agent-collaboration-plan.md)。

**续轮规则：** 默认每轮六次调用由 root 内部管理，综合结果后依据新证据缺口自行组织下一轮；用户设定的总调用、费用、时间和资源限制跨轮累计，不得重置绕过。

**静态验证（2026-11-02）：** 仓库检查器通过 15 个 Agent、26 份文档、48 个本地链接和 11 个负向用例；相关文件编辑器诊断无错误，`git diff --check` 通过。以上不验证实际会话提问频率、运行时权限或自主续轮行为，问题保持待验证。

**待验证场景：** 用户要求推进具体项目时，Agent 应不再逐项询问代码修改、隔离依赖安装或训练许可，并完整记录；进程失败时只处置自身且身份已确认的任务；系统/共享环境、用户脏改动、原始数据、健康任务和外部发布仍受保护；仅对确实超出上述授权或会改变科学含义的动作询问。

### AC-006：自主入口仍按有限批次主动收工

**触发与影响：** 用户明确希望“持续自动研究，看到后主动终止并检查”。原入口的停止条件包含目标完成、没有有区分力的新检查、所有工作阻塞和单轮额度处理逻辑，整体更像有限批次执行；这会让 Agent 在一个小目标或一轮派工结束后主动汇报，而不是围绕同一研究问题寻找下一项工作。这里仍保留“没有任何可保留且不重复的研究路径”这一窄停止条件，避免无限重复同一检查。

**用户决定与处理：** 自主模式现改为用户中止式持续研究：完成阶段、实验、分支返回、暂时没有 ready 子任务或用尽单轮调用额度都不自动结束。root 应回到研究问题，持续生成下一项有区分力的调查、实现、验证或实验；六次调用只是单轮内部扇出限额，不是总任务上限。用户可以主动要求检查、暂停、终止或改变运行方式，Agent 再提交阶段报告；用户明确设置的总上限、研究含义变化、越出授权、真实安全/权限/宿主运行时阻断仍优先。

**运行时边界：** 持续是当前 Agent 会话能够继续时的行为要求，不代表跨窗口常驻守护或自动唤醒。长实验按执行规范独立运行并留下可恢复身份；停止 Agent 的迭代不默认终止健康外部实验。

**修改位置：** [自主入口（历史名称）](../agents/research/entry/autonomous-research-orchestrator.agent.md)、[共享协作协议](../research-guides/orchestration.md)、[总体规划](research-agent-collaboration-plan.md)、[用户层规格](../COPILOT_USER_LAYER_SPEC.md)。

**待验证场景：** 一个子目标完成后继续派发下一项有区分力的工作；一轮六次调用结束后不询问用户而自行续轮；用户要求检查时暂停新增派工并汇总；用户要求停止时不默认杀掉健康运行；当前会话无法继续时返回可恢复状态而不声称跨窗口常驻。

3. 状态采用“待实施 → 实施中 → 待验证 → 已关闭”；需要外部条件时记“阻塞”，不再成立或被替代时记录原因。每次更新注明核对日期。

5. 具体问题状态只在本文维护；规划保留入口和架构决定，验收记录保留实际命令、轨迹和运行结果。读取维护问题时进入本文，执行研究任务仍读取正式 Agent 与协议。

## 文档批注如何高效交互

继续使用 `> user comment:` 即可，不需要额外语法。批注放在对应问题下；跨问题或批量指示时引用 AC 编号。文档保存后，在聊天中说“处理这份文档里的新批注”，即可触发读取。

可在批注开头加一个可选意图标签，后面照常写自然语言：

| 意图 | 写法示例 | 如何处理 |
|---|---|---|
| 认可方案 | `> user comment: 同意：AC-001 按推荐方案处理。` | 记录方案确认；不标成已实施或已验证。 |
| 提出问题 | `> user comment: 提问：AC-003 如何避免反复核查？先不要修改 Agent。` | 回答并补充建议，未确认的新方案单独标出。 |
| 修订方向 | `> user comment: 修改建议：允许局部验证，不要增加固定审批角色。` | 更新方案和原因，保留原批注及决定演变。 |
| 明确执行 | `> user comment: 执行：实施已同意的 AC-001、AC-002、AC-004，并验证；AC-003 先不动。` | 按明确范围实施与验证，遇到实质范围或权限变化再询问。 |

**最省事的流程：** 在文件中批注并保存，然后在聊天中说明“只回应”或“直接实施已同意项”。不需要重新粘贴整份文档。仅在本地保存不会自动触发 Agent 处理；需要在聊天中明确要求处理。

**回复与维护：** 简单问题在批注附近补简短回应；涉及方案变更时更新正文和状态，注明由哪条批注引起，不逐段复制长回复。保留用户原话，不把引用的第三方或旧 AI 回复当成用户指令。存在连续多轮讨论时按需追加日期或小编号，不强制每条批注填写表格。旧的“同意”不会自动批准随后新增的实质方案；“同意并实施”或等价明确表述则直接推进，不再重复索要同一授权。
