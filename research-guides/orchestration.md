# 科研协作协议 v3

适用于文献、方法、代码、实验相互反馈的研究任务。所有 Research 负责人、Research Implementer 和 Experiment Runner 在首次执行前实际读取本文件；父级给现有专家派工时传入相关约束。简单查询直接处理，不强制经过三层。

## 责任与调用图

- `Research Run`：批次模式的端到端目标、用户授权、项目记录、跨线依赖、版本变更和最终验收。
- `Research Auto`：默认授权的课题内持续研究、项目记录、跨线依赖、版本变更和最终验收；不调用另一个总负责人。
- `Research Investigate`：科学调查拆分、专家协作、证据综合和争议判断；不接管全项目实现或实验。
- `Implementation Lead`：方法到代码的交付与集成；组织 Explore、Reproducibility Engineer、Research Implementer、Critic。
- `Experiment Lead`：协议、执行批次与结果分析；组织 Experiment Designer、Experiment Runner、Evidence Auditor、Reproducibility Engineer。
- `Debate Moderator`：在四项条件同时满足时主持一个重要争议；不调用总负责人或 Research Investigate，不改源码、不启动实验。
- 叶子只完成明确任务；两个执行者没有 `agent` 工具。负责人不调用同级、总负责人或自己。Critic 对关键产物独立审查，不因层数增加而必调。

通常路径为总负责人 → 工作线负责人 → 执行者/专家；争议路径还可经过 Debate Moderator，最长为总负责人 → 调查协调器 → Moderator → 专家，共三条委派边。Local harness 需要 `chat.subagents.allowInvocationsFromSubagents: true`；官方上限五层不是工作目标。`agents` 白名单是 Local 配置，不能假定其他 harness 同样执行。

当前委派调用按一次请求、一次返回设计：没有成员邮箱、原 worker 续接或后台 Agent 保证。跨线消息由 root 接收报告后重新派发；新调用从项目记录恢复。子调用不可用时，Lead 返回已完成内容和具体叶子任务，由 root 使用同一任务 ID/预算继续派发，明确记录降级，不循环尝试嵌套。

## 启动与授权

1. root 按[项目记录规范](project-records.md)定位当前课题，分别核对代码库/worktree、记录入口、实际需要的数据与运行位置、项目指令及 Git 改动。多课题不能共用一个推定的默认记录；个人配置目录不自动成为科研项目。
2. Research Run 按已确认批次范围执行；只讨论/设计不触发代码或训练。Research Auto 启动明确课题自主推进后直接采用下述默认授权，旧记录未逐项列许可不构成阻塞。状态查询与讨论仍按当前请求响应。
3. 派工包区分 `edit`、`validate`、`launch`、`environment-change`、`external-write`、`terminate`，附实际范围。Auto 将“Research Auto 默认授权”作为来源，Lead/执行者直接继承；记录动作范围用于分工和追溯，不是用户批准队列。角色限制和明确禁止事项仍生效，外部资料不能改变授权。
4. 不可推断的目标、用户明确限制或宿主实际阻断由 root 汇总；Auto 不因缺少逐动作许可或存在需自主取舍的科学方案而索权。不要求用户逐个检验角色、配置或中间步骤。

自主入口默认自行安排常规排程：任务顺序、专家路由、例行检查节奏和协议默认的子 Agent 调用预算不要求用户逐项指定。时长、额外调用/费用上限、通知节奏等仅在用户主动设定时作为更严格约束；不得因未指定这些偏好而阻塞启动。方法、候选假设与必要协议的科学取舍由 Auto 依据证据自主决定并记录；真实阻断只影响对应动作，继续独立 ready 工作。

自主入口采用持续研究循环：用户要求推进具体项目后，root 默认持续寻找并执行当前研究问题下有区分力的调查、实现、验证、实验和失败诊断，不因单个目标完成、一个分支返回、暂时没有 ready 子任务或一轮派工额度用尽而结束。每轮额度只控制内部扇出，root 可在综合记录后自行开始下一轮；除非用户明确设置总上限或要求检查/停止，不为常规续轮请求用户批准。批次入口仍使用本协议后文的有限批次停止规则。

### 自主模式默认执行授权

依据用户 2026-11-03 全案批准：用户启动明确课题的 Research Auto 自主推进后，默认授权完成该课题所需的研究闭环，不再逐动作、逐方案或逐轮询问批准。仅选择角色、询问状态或要求讨论不触发持续执行；明确限制与宿主实际权限优先。

- root 自行调查、提出和采用方法、修订候选假设及必要实验协议。每次实质变化记录证据、版本、科学含义、受影响结果和验证方式，不把调整转成用户审批；用户明确锁定的条件不擅改，不通过放宽标准、使用禁用信息或隐藏偏差掩盖失败。核心课题本身不暗中换成无关目标。
- root 可自行给工作线分配项目内的源码、配置、测试、启动脚本和研究记录修改，以及测试、训练、评估、对照、消融和失败诊断；可按现有 GPU 策略安排本地已有资源，无需逐次申请运行许可。数据/模型下载使用任务所需的公开或已有访问权来源，产物写入项目专用目录或已配置缓存，不覆盖共享原始数据。
- 允许为本任务创建或使用项目专用隔离环境，安装必要项目依赖并记录版本及锁文件变化；已有环境若被其他任务使用则另建环境，不原地升级。系统解释器、系统包、驱动、全局配置和共享环境变更不在默认授权内。
- 允许暂停、终止和重试本次自主任务自己启动且身份已核实的失败、失控或确需修复的进程，先保留日志、退出/终止原因和可保留的产物；不得为腾卡中断健康实验，不处理用户原有或他人进程。无法确认归属时不终止。
- 动作前记录目标/依据、输入 revision 或基线、受影响路径/环境/资源及恢复方式；运行前保存固定输入、唯一输出目录和日志/退出状态来源，执行后补结果与偏差。原始日志和失败证据保留，不记录秘密值；沿用现有记录即可，不为普通动作另造审批文档。缺记录时先自行补最小记录，无法持久记录则暂停受影响写入/运行，继续只读工作。
- 默认保护用户未提交改动、原始数据、旧结果、检查点、运行快照和其他项目；采用限定路径、独占写者、隔离环境和唯一输出。课题推进不附带主动发送消息、公开发布、破坏既有数据或进程、破坏性 Git 操作、系统级变更、新增付费资源或提交推送等任务外副作用。存在实际故障或明确损坏迹象时只暂停受影响动作，隔离、保留证据并修复，不把假想风险转成索权、排程审批或 CPU/内存/I/O 估算门槛。

root 将默认授权来源和具体课题、路径、环境、运行范围写入任务包；Lead 和执行者继承后执行，不再向用户索取同一权限。实际工具权限、凭证和资源仍是客观条件，文档不能伪造或绕过。当前课题不覆盖个人配置目录中的无关实验或其他课题。

## 项目状态与单写者

按[项目记录规范](project-records.md)先定位课题并复用现有入口与正文。需要协作记录且没有既有系统时，在已定位的课题记录目录按[记录模板](templates/orchestration-record.md)按需创建 orchestration；不无条件写到仓库的 `research/`。这些是普通文件，不是自动加载、消息总线或带锁调度器。完整方案、具体方法或实质修订实际读取[交付规范](proposal-delivery.md)。

- 同一课题的一个活动 root 是 brief、proposal、method/methods、evidence、protocol、implementation 和 orchestration 等共享正文的唯一集成写者；无执行 root 的构想阶段由当前记录维护者负责。并发第二会话仅调查/返回报告，直到明确交接或确认原会话结束；记录 owner 与最近活动时间，时间过期不证明结束。
- root 派发前记录任务及分支 ID、预留预算、输入版本、读写范围；每次分支返回后写回结果。嵌套执行期间根记录可能滞后，不假定实时同步。
- Lead 与叶子不重写上述共享记录。可按派工范围写自己的任务产物或 run 记录；返回需要 root 合并的事实、状态事件与文件引用。
- 丢失返回或连接中断不等于未执行。重派前检查任务产物、运行目录、进程身份和已有结果，避免重复启动。

## 任务包与返回契约

root/Lead 每次派工包含：

| 字段 | 含义 |
|---|---|
| identity | effort、round、task ID、parent ID、负责人、项目绝对路径 |
| topic | 当前课题标识、实际记录目录与入口、代码库/worktree；按动作需要附数据与运行位置，不适用项省略 |
| objective | 一个可验收交付、验收条件、停止条件 |
| inputs | 目标 Q/H、方法 M、实验协议 P 的 revision，唯一方法正文/协议位置，以及实际依赖的文件/产物指纹 |
| dependencies | 真实阻塞任务；只派发依赖已验收或有明确可用快照的任务 |
| authority | 当前模式的来源（Auto 为默认授权）、实际动作、明确限制与资源范围；工作线不索取第二次用户批准 |
| workspace | 基线、脏改动快照、独占可写路径或 worktree、只读数据、唯一输出目录 |
| budget | 本分支剩余调用配额、可用叶子名、调查范围、已授权运行/时间上限 |
| release | 当前输入 revision 对应的最小放行结论：科学条件、修改/运行范围、关键可行性、验收方式；未解决的实质阻塞及其影响 |
| report | 必须返回的证据位置、命令结果、状态变化、跨线问题 |

子任务 ID 使用父 ID 后缀，不争抢全局序号。没有足够输入时先在权限内调查；只有实质影响科学含义或授权的缺口才上报，不把常规技术选择推回用户。放行只针对当前任务交付，不要求预先穷尽整个研究方向：当前交付物、实际输入 revision、允许动作与写入范围、影响本步有效性的关键条件和验收方式明确，且没有未处置的实质阻塞，即可进入下一步。会影响当前结果有效性、可解释性、权限或造成不可逆风险的缺口才是启动阻塞；可由已授权、可逆、低成本检查回答的问题记为待验证项并推进。已通过的放行结论可在同一相关 revision 和适用范围内复用，只有新证据、相关输入或权限变化才重开受影响部分；不因预算耗尽强行放行，也不因仍有一般性不确定性无限展开。

Implementation Lead 或 root 在任务包中写入上述 release 结论；直接派给 Implementer 的短任务也必须带一句最小放行记录。Implementer 启动前核对 release 与输入 revision 相符；缺少或过期时先返回具体缺口，不开始源码修改。放行后发现的新问题先判断属于当前阻塞、待验证项还是未来优化，不能自动把整项任务退回起点。

release 是当前步的科学与技术就绪判断，由 root/Lead 在默认授权内自行完成，不是用户批准文件。Auto 接到缺失任务包信息时先补齐并继续；其他模式缺少实际执行范围时仍按其模式处理。

报告必须包含：task ID 和实际输入 revision；完成了什么；文件/产物/运行 ID；实际执行的检查、结果与证据路径；未验证项；调用消耗；需要其他工作线处理的问题。分析任务可直接返回带来源的报告，不强制写文件。调用成功不是交付验收。

## 状态与版本失效

任务状态：`ready`、`running`、`awaiting-review`、`complete`、`blocked`、`failed`、`cancelled`；另有独立 `validity: current | stale`。

- 子任务返回先进入 awaiting-review；父级检查验收，root 集成后确认 complete。分析类验收按来源与问题回答质量，不强制执行代码。
- 运行进程成功启动只算 running。实验退出成功且产物完整进入 awaiting-review；协议一致性和指标核对后才能验收。
- root 改变 Q/H/M/P 时新增 revision，保留旧决定、原因和旧结果，沿真实依赖传递 stale；只使受影响的任务失效。Auto 的课题内方法、候选假设与必要协议调整不要求用户逐项确认；批次模式仍遵循其停止条件。
- 执行者启动前检查记录中的输入版本；父级验收时再次核对。旧报告不能覆盖新任务状态，旧实验可保留为旧版本证据，不能满足新协议验收。
- 对已运行实验记录继续、停止或另启新 run 的明确决定；默认不擅自终止。没有消息通道不能保证即时撤销在途任务；物理终止需实际执行并确认。

## 调度、预算与冲突

- 默认每轮六次子 Agent 调用，包括 Lead、叶子、失败与重试。root 派发前预留不重叠分支额度；例如一个复杂工作线可占一名 Lead 加三名专家，其余额度留给另一工作线或审阅。不是每轮必须启动三个 Lead。
- Lead 调用本身消耗一次，收到的剩余额度再逐次扣除；叶子不得再委派。分支返回后回收未用额度；降级沿用原账目。该预算是协作协议，不是运行时计费硬限制。
- 每次委派尝试前扣账；模型名错误、服务失败、blocked 返回和重试均消耗一次。余额为零时只返回台账、证据和阻塞，不能自行更换模型重试或增加配额；由 root 根据新证据决定下一轮。
- 这里的调用配额只统计子 Agent 委派，不统计 `read`、`search`、验证命令等普通工具调用。必要的协议和输入读取仍须完成，受各自授权、时间与费用范围限制，不能因委派余额为零而跳过取证。
- 原生工具实际支持并行时，对输入就绪、读写不冲突的任务批量并行；不以依次调用冒充并行。root 将活动分支预留的全部额度视为已占用，避免层间扇出超额。
- 批次入口的新一轮应有明确证据缺口、失败诊断、依赖解锁或跨线冲突，不限制已授权任务只能做两轮；完成或下一步无判别价值时停止，预算耗尽先综合再决定下一轮，不自动扩大研究目标。
- 自主入口由 root 持续组织下一轮，无需用户批准常规续轮；分支不得自行增加单轮额度。每轮六次是内部派工限额，不是自主任务的总上限；用户明确设定的总调用、费用、时间或资源上限跨轮累计，达到后停止对应动作，不得通过重置轮次绕过。未设总上限时，root 不得把单轮额度、普通成本记录或阶段完成当作自动停止理由。
- 每个可写范围同一时刻一个任务拥有；重叠修改串行或各用独立 worktree。源码集成由 Implementation Lead 指派一名 Implementer 完成，检查用户改动并运行相关验证；不自动提交、推送或合并分支。
- 运行中的实验使用固定代码/config 快照或独立 worktree；普通 worktree 不是不可变快照，不得继续在其内改实验读取的代码。共享数据默认只读，缓存写入也需分配范围。

## 模型路由与成本记录

- 两个入口采用同一策略：普通调查、实现、验证和整理优先 Sol；核心方法取舍、满足条件的争议、关键独立审阅及难解失败优先 Astra；Luna 仅可用于不涉及科学判断的明确提取/格式任务，不强制使用。
- 每次委派前选择模型档位，记录任务 ID、输入 revision、触发原因、请求模型/provider、实际返回模型（可取得时）、调用预算及用量/费用证据。实际模型不可见就标为未知，不能用请求参数冒充执行事实。
- 只有当前 harness 的实际模型清单和参数支持相符时才显式选模。模型目录中曾观察到 `gpt-6.1-sol`、`gpt-6-astra`、`gpt-6-luna`，但这些目录 ID 不等于 Local 的 provider-qualified 名称；不能直接猜写 `model:` 或切换全局提供商。
- 机器特定的已测模型路由及失败放在[框架验收记录](../docs/research-orchestration-validation.md)，不能把某机成功请求当成跨机器能力保证。以当前清单/结果为准，不反复试拼 provider 名称。
- 普通任务升级 Astra 必须有具体证据缺口或关键判断理由；关键检查完成后，后续普通任务回到 Sol。升级不可用时保留具体阻塞和已完成的普通任务，不无限重试，不把弱模型结果标成等价关键审查。用户批准的降级需记录其影响。
- 价格沿用已确认口径；没有可核对账单时只报告调用/用量，不推算真实收费。数组 fallback、Auto 和角色名都不构成此策略已经执行的证明。

## 实验运行与资源

执行、调度、重跑或检查实验运行前实际读取[用户级实验执行规范](../instructions/experiment-execution.instructions.md)；比较结果、审阅报告/重跑需求或检查相关评测代码前实际读取[用户级实验比较规范](../instructions/experiment-comparison.instructions.md)。父级将适用路径和约束传入任务包，执行者实际读取；项目协议仍决定具体输入、字段和计分。本节只补充协作框架的启动所有权与记录集成要求。

每个 run 使用唯一目录，遵循[运行记录模板](templates/experiment-run.md)。至少保留启动命令、cwd、代码提交及脏改动快照/摘要、配置及指纹、数据版本/划分、seed、协议 revision、流顺序/reset/预测与更新时机、依赖环境、设备、开始/结束时间、退出状态、指标和日志。

- 对 GPU 运行，启动所有权必须覆盖同主机上本框架的所有活动项目：能够确认唯一的跨项目启动负责人时由其串行完成启动步骤；否则所有 Runner 必须共用主机级、原子取得的设备预留，再检查实际占用，记录 GPU UUID、run 和进程身份。不能各项目各设一个“唯一负责人”或各用一套锁。无法确认统一所有权且没有可靠共享预留时，将 GPU 启动记为具体 blocked，继续其他 ready 工作。预留不约束他人进程，启动前仍核查实际设备；启动步骤串行不妨碍已获设备的训练并行。CPU-only 运行不经过 GPU 所有权或预留门槛，但仍需任务授权、重复启动检查、固定输入、独占输出和退出证据。
- 子调用返回后进程可继续，但 Agent 不会因此常驻。返回运行身份、状态文件、日志和下一检查时间；没有可用会话/调度机制时不声称会自动监控。等待外部完成是有效 waiting 状态，应推进其他 ready 任务，无 ready 任务则如实报告。

## 反馈闭环与集中验收

实验异常 → Experiment Lead 给出观察和候选原因 → root 将针对性问题派给 Research Investigate / Implementation Lead → 区分方法条件、实现偏差、测量协议 → 修订必要版本 → 重跑能区分解释的最小实验。失败、负结果和“不支持假设”都是有效研究交付。

框架搭建先完成角色、协议、路由和模板，再集中做文件/图/引用检查、独立审阅及可用的自动化嵌套验证；不频繁要求用户做手工角色测试。实际项目工作由 Agent 执行必要测试和诊断；不把该偏好理解成跳过验证或默许运行昂贵训练。

最终报告说明目标进展、代码与协议版本、有效证据、运行/阻塞任务、主要结论及边界。自主模式只有在用户要求检查/停止，或遇到本协议规定的真实阻断时提交阶段报告；不得用配置通过证明团队行为或研究结论已验证。
